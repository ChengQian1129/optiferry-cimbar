## Scope of remaining validation

No OPPO Find N5 or Android emulator/instrumentation execution was available. MediaStore Direct/fallback writes, collision behavior, camera runtime, Android OS process killing, device RSS, segment-boundary latency, 100/512 MiB zero-touch optical transfer and useful throughput have **not** been verified on-device.
Journal and restart tests use the real shared journal implementation plus a JVM random-access file fixture, not a mocked complete MediaStore provider. They do not establish device-provider correctness.

The original 32-bit session requirement conflicts with the 16-bit upstream wire field. The compatibility amendment and batch-count bound are explicit in UPSTREAM_COMPAT.md. This is a usable first-build delivery, not a declaration that every original P0 hardware acceptance item has passed.

Additional memory check: 512 MiB sparse source, 64 default 8 MiB segments, native frame export to /dev/null completed with maximum RSS 30,688 KiB. This measures sender preparation/encoding, not Android or GPU/window RSS.

Post-change verification: real qsend output for a 100 MiB file (13 segments) passed the JVM suite with 20% erasure, reordering, duplicates, rotating passes, and simulated restart. The receiver now bounds active decoders to four sessions and replays older session frames from an app-private journal. ## User-reported OPPO optical sample — 2026-09-11

The OPPO PKH110 / Android 16 samples consistently report 3.74–3.88 valid transfer QR hits per analyzed frame, zero camera-analysis drops, and 8.3–12.2 ms average decode. Spatial recognition and the decoder are therefore healthy. Across the reported sessions, accepted new sequences are about 616/42.8 = 14.4/s, 1479/106.5 = 13.9/s, and 2180/155.4 = 14.0/s. With the 2068-byte frame format's 2048-byte payload, that predicts about 28.7 KiB/s—the observed 28–30 KB/s. `--repeat 3` did not materially change this rate, which points to display transition/rolling-shutter sampling rather than CameraX CPU capacity. The live “速度” value is a de-duplicated QR-payload rate, not completed useful-file throughput; completed segment/file rates are the meaningful transfer metric.

The later physical dual-code trial (`--dual --attempt-factor 1.65`) is a regression, not an improvement: after 10:03.7 it reported 4,484 valid AFL2 decodes but only 260 unique sequences (520 KiB), 2,215 multi-code hits over 2,322 scans, and 1,095 complete/259 partial dual observations. The camera still ran at 60 FPS with zero drops and 5.5 ms average decode, so the loss is in optical frame transitions/visibility of new content. Keep the normal or stable-lanes four-code profile for the next comparison; do not use dual as the default speed profile.
